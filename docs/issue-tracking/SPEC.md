# SPEC — `sadhanayog-track@0.1`

The format. One markdown file per issue, YAML frontmatter, git as the transport.

This is an **OKF 0.1 profile**: every issue file is a conformant OKF *concept document*, so a
generic OKF consumer can read this bundle without knowing anything about issue tracking. The
tracker-specific keys ride along as spec-sanctioned extensions.

---

## 1. Why a file, and not a database

The database is the filesystem. That is the whole design.

| Property | How the file format gets it for free |
|---|---|
| **Versioned** | `git log docs/issue-tracking/issues/SY-0010.md` is the issue's full history, with authorship and diffs. No audit table. |
| **Branchable** | An issue's state can differ on a branch and merge with the code that changed it. A PR can move its own ticket. |
| **Reviewable** | Scope changes show up in code review as a diff, next to the code. |
| **Offline** | It is a text file. |
| **Agent-native** | An agent already has `Read`, `Edit`, and `Grep`. It needs no API token, no MCP server, and no rate limit to file, triage, or close an issue. |
| **Un-lock-in-able** | If this tool is deleted tomorrow, you still have the markdown issue files. |

The cost is real and worth naming: **no realtime multiplayer, no cross-repo view, no mobile app,
no notifications.** If those matter more than the five properties above, use Linear. This format
exists because for a repo whose work is *executed by agents inside the repo*, they don't.

---

## 2. OKF conformance

Source: Google's OKF v0.1 (`GoogleCloudPlatform/knowledge-catalog/okf/SPEC.md`).

| OKF requirement | How we satisfy it |
|---|---|
| Bundle = a directory tree of markdown concept documents | `docs/issue-tracking/` |
| Every non-reserved `.md` has frontmatter with a non-empty `type` | `type: Issue`, `type: Project`, `type: Template` |
| Recommended: `title`, `description`, `tags`, `timestamp`, `resource` | All present. `resource` points at the design doc that owns the work |
| Concept ID = bundle-relative path minus `.md` | `issues/SY-0010` |
| Reserved `index.md` — the catalog | Generated by `track.mjs index`; group headings plus catalog bullets |
| Reserved `log.md` — dated entries, newest first | Hand-maintained decision log |
| **Consumers must preserve unknown fields** | `serializeDoc()` re-emits every key it did not recognize, verbatim, after the known ones |
| Producers may add keys | `status`, `priority`, `cycle`, `blocked_by`, … are our extensions |
| Permissive consumption | `track.mjs` tolerates missing optional fields; only `type`/`id`/`title`/`status` are hard-required |

**The one deliberate deviation.** OKF-Hub's KOM namespaces platform extensions as `x-hub-*`.
We use **bare keys** (`status:`, not `x-track-status:`), because humans and agents hand-edit these
files constantly and `x-track-` on every line is a tax paid on every write for a benefit
(collision-avoidance) that a single-bundle format does not need. OKF's unknown-field-preservation
rule means a generic consumer still round-trips them losslessly — which is the property that
actually matters. If this bundle is ever published to an OKF registry alongside others, the
adapter renames on export; nothing in the tracker knows or cares.

**Labels are stored in OKF's native `tags` field.** There is no separate `labels:` key. The UI
calls them labels because that is what they are called everywhere; `config.yml` attaches the color
and the group. One field, no derivation, no drift.

## 3. The YAML subset

`track.mjs` ships its own ~120-line parser rather than taking a dependency. It supports exactly:

- nested maps by indentation
- block lists (`- item`) and lists of maps (`- id: x`)
- flow lists and maps (`[a, b]`, `{a: 1}`)
- scalars: string, quoted string, integer, float, `true`/`false`, `null`/`~`
- `#` comments (at line start or after whitespace, not inside quotes)

It does **not** support anchors, aliases, multi-line scalars (`|`, `>`), multi-document files, or
complex keys. `track.mjs lint` fails on anything outside the subset, so a file cannot silently
drift into something the parser mis-reads.

Dates are kept as **strings**, never parsed into `Date`. No timezone surprises, byte-stable
round-trips.

## 4. The issue document

```yaml
---
type: Issue                        # OKF: required
id: SY-0010                        # must equal the filename
title: Workspace/toolchain scaffold
description: One sentence.         # OKF: recommended
status: ready                       # → config.yml states
priority: P1                   # → config.yml priorities
estimate: 5                       # → config.yml estimate_scale
assignee: unassigned                  # → config.yml members
project: stage-1                  # → projects/*.md
milestone: Stage 1          # free string; the phase inside the project
cycle: stage-1                     # → config.yml cycles; null = unscheduled
rank: 40                           # optional pick order (lower = higher on board / earlier in `track next`)
tags: [task, docs, agent-ok] # → config.yml labels
parent: null                       # → another issue id (sub-issue)
blocked_by: [SY-0008]              # → issue ids
blocks: [SY-0011, SY-0014]         # → issue ids (the mirror of blocked_by)
relates: []                        # → issue ids
resource: docs/architecture/engineering-foundation.md   # OKF: the design doc that owns this
linear_id: null                    # optional cross-link to the live Linear workspace
branch: null                       # git branch, once work starts
pr: null                           # PR number, once open
created: 2026-07-11
timestamp: 2026-07-11T09:00:00Z    # OKF: last change. Written by the tooling
---

## Context
Why this exists. Cite files and lines.

## Tasks
- [ ] Each checkbox is a sub-task.
- [ ] The board reads these as the `0/8` progress ring.

## Verify
- [ ] The observable behavior that proves it works.
```

### Rules the tooling enforces (`track.mjs lint`)

1. `id` must equal the filename. `SY-0010` lives in `issues/SY-0010.md` or, after a deliberate
   move, `archive/SY-0010.md`.
2. Every enum value must exist in `config.yml`. An unknown `status`, `priority`, `cycle`,
   `assignee`, `estimate`, `project`, or label is an **error**, not a warning.
3. Every `blocked_by` / `blocks` / `relates` / `parent` reference must resolve to a real issue.
4. **Relation symmetry.** `A.blocks: [B]` ⟺ `B.blocked_by: [A]`. A one-sided edge is an invisible
   dependency — the board draws from either side, so the graph would lie. Lint errors on
   asymmetry. Declare the edge once in `blocked_by`; `set`/`new` mirror `blocks` on the peer.
5. **No dependency or parent cycles.** If A blocks B blocks A, or A is parent of B is parent of
   A, nothing can ever start. Lint reports the loop.
6. `status: blocked` requires a non-empty `blocked_by` — name what blocks it.
7. `status: duplicate` requires a non-empty `relates` — name the survivor.
8. Label groups marked `exclusive: true` in `config.yml` (`kind`, `surface`) permit at most one
   label each.
9. `status: done` requires checked Acceptance Criteria, non-placeholder Review Evidence, and
   the Completion Checklist items for acceptance and verification commands. `move`/`done`
   refuse the transition without that evidence.
10. `next` returns only `ready` issues whose every blocker is terminal (`done`, `canceled`,
    `duplicate`). `next --all` also lists unblocked `triage`/`backlog`/`todo`.

### ID allocation

`max(existing) + 1`, zero-padded to four digits (`SY-0001`). There is no
counter file to drift or conflict on merge.

**This is why an issue is never deleted.** Close it as `canceled` or `duplicate`. Deleting
`SY-0042` would make the next issue reuse the number, and every git commit, branch name, and
cross-link that mentioned the old `SY-0042` would silently point at a different thing.

## 5. Derived, never stored

Two things the board shows are computed on read and never written to a file:

- **Task progress** (`0/8`) — counted from the `- [ ]` / `- [x]` lines in the body. Editing the
  markdown by hand updates the ring. There is no `tasks_done:` field to fall out of sync.
- **`blocks`** — the mirror of `blocked_by`. It *is* stored (so the file is readable standalone and
  greppable in both directions), but it is generated from the reverse edges and lint keeps it
  honest. Declare a dependency once, in `blocked_by`; let the tooling mirror it.

## 6. The project document

```yaml
---
type: Project
id: stage-1
title: Repository and engineering foundation
short: S1                       # what the board's project chip renders
description: One sentence.
initiative: foundation           # → config.yml initiatives
color: "#5e6ad2"
status: planned
lead: unassigned
resource: docs/architecture/engineering-foundation.md
created: 2026-07-11
timestamp: 2026-07-11T09:00:00Z
---
```

A project is a thin pointer. **The design lives in `docs/`, not here.** The project document exists
so the board has something to group by and so `index.md` has a heading — it is not a second place
to write the spec. When a project document and its `resource` guide disagree, the guide wins.

---

## 7. `config.yml` is the schema

Every enum an issue may reference is declared in `config.yml`: states (with categories that drive
board behavior), priorities (with sort order), estimate scale, labels (with colors and exclusive
groups), cycles (with date ranges), initiatives, and members.

Columns on the board are derived from **config, not from the data** — so an empty cycle still
renders as an empty column. That is what makes the board a plan and not just a report.
